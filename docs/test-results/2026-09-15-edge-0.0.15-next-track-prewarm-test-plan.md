# Edge test plan — 0.0.15 next-track prewarm

Target: Microsoft Edge + Violentmonkey

## Purpose

Validate the conservative 0.0.15 optimization that prepares the next Google Drive row before the current track finishes, while preserving the validated 0.0.14 background-transition recovery.

This build does **not** directly preload the next media stream. It pre-resolves and, when needed, positions the next queue item's Drive row at about 85% progress so the end-of-track transition can skip part of the row-discovery work.

## Setup

- Enable only `google-drive-folder-player.user.js` version 0.0.15 from `dev/0.0.15-next-track-prewarm` as the main player.
- Keep `probes/background-playback-probe.user.js` 0.0.2 enabled if desired; it remains passive.
- Refresh Google Drive.
- Use the same mixed MP3/WebM folder used for 0.0.14.

## Foreground prewarm test

1. Scan the folder and start continuous playback.
2. Let a track play normally past about 85%.
3. Watch the green playback status. Expected indicator: `next ready` when a reusable next row was prepared.
4. The diagnostic box should contain a line beginning with `Prewarmed track ...` when preparation succeeds.
5. Let the track finish naturally.
6. Confirm the next track opens correctly and the diagnostic reports `Using prewarmed Drive row ...` before the normal transition messages.
7. Compare the perceived silence/loading gap with 0.0.14. The goal is a shorter and less visually obvious transition, not guaranteed gapless playback.

## Shuffle test

1. Enable Shuffle and start a new queue.
2. Let several tracks reach the prewarm point and finish naturally.
3. Confirm the prewarmed target always matches the next item in the displayed shuffled queue.
4. Confirm no queue item is skipped or duplicated because of prewarming.

## Repeat regression

- Repeat ONE: the prewarm target should be the same current track; natural end must still restart it.
- Repeat ALL: at the last queue item, the prewarm target may be queue item 1; natural end must still wrap correctly.
- Manual `Next now` must continue to work even if the prepared natural-end target differs from the manual target.

## Background regression

1. Start playback and put the Drive tab in the background.
2. Let at least 3–5 natural transitions occur.
3. Confirm the 0.0.14 guarded background recovery still works and playback does not stop at a delayed preview-close confirmation.
4. If background playback stops, do not refresh; capture both the main player diagnostics and Background Playback Probe log.

## Expected result

- 0.0.15 remains functionally identical to 0.0.14 except for next-row preparation beginning around 85% progress.
- Successful preparation shows `next ready` and `Prewarmed track ...` diagnostics.
- Natural transitions can reuse the prepared row when it remains valid; stale rows automatically fall back to the normal 0.0.14 resolution path.
- Shuffle, Repeat, WebM hidden-range detection, draggable panel, and guarded background transitions remain unchanged.
- No userscript permission changes; still `@grant none` and no Google API.

## Interpretation

If transitions feel materially smoother, this optimization is worth keeping. If the audible gap remains almost unchanged despite successful `next ready` diagnostics, the remaining delay is likely dominated by Google Drive closing/opening the preview and loading the media itself rather than by row discovery. That would require a separate experiment; do not change the 99.5% end threshold in this test.
