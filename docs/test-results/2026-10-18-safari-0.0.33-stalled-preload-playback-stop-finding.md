# Safari + Userscripts — 0.0.33 stalled preloaded-next playback stop finding

Date: 2026-10-18

## Owner observation

During unattended queue playback, playback stopped after track 6/172 ended.

UI status reported that track 7 could not be loaded.

The owner notes that similar spontaneous stops were observed in earlier versions as well.

## Debug evidence

The relevant sequence was:

- `Natural end: 6/172 [WEBM].`
- `Promoting preloaded 7/172.`

No subsequent metadata / Playing event for track 7 appeared.

The player then reported:

`Track could not be loaded: ...mp3`

Track 6 remained shown at 100%, making the transport state look stale after the failed transition.

## Root cause in current control flow

When `playIndex()` promotes `directNext`, it waits up to 6 seconds for the promoted slot to become ready.

If that promoted/preloaded media element is stalled, no longer ready, or otherwise fails the readiness check:

- the promoted slot is disposed;
- `playIndex()` returns false;
- no fresh media element is created for the same target;
- natural auto-advance therefore terminates at that point.

This is a playback-resilience gap rather than a playlist/discovery issue.

## Planned 0.0.34 recovery

Keep the normal preload path unchanged.

Only when a promoted cached/preloaded slot fails readiness:

1. dispose the unusable promoted slot;
2. create a fresh current media element for the same target track;
3. wait using the normal fresh-load timeout;
4. continue playback if the fresh retry succeeds;
5. only report a real load failure if the fresh retry also fails.

Also refresh playback/transport/Media Session state on unrecoverable failure so the UI cannot appear to remain actively playing.

The frozen Edge 0.0.28 branch remains untouched.
