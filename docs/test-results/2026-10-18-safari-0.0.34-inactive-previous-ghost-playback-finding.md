# Safari + Userscripts — 0.0.34 inactive previous-slot ghost playback finding

Date: 2026-10-18

## Owner observation

0.0.34 resolved the earlier unattended playback-stop problem.

A new/now-visible problem occurs intermittently:

- the intended current track continues playing under normal player control;
- the immediately previous track can also become audible at the same time;
- that second/previous playback is not controlled by the visible player transport;
- the exact trigger is not yet known.

## Assessment

The strongest code-level suspect is the bounded previous-track cache introduced in 0.0.33.

Unlike older versions, the previous media element is intentionally kept alive instead of being disposed. The UI controls only `directCurrent`; a cached `directPrevious` HTMLMediaElement exists outside that visible current-control path.

Safari/macOS also manages system Media Session ownership around these HTMLMediaElements. Even though cached slots are explicitly paused, an inactive but live element must be treated defensively so that any browser/system reactivation cannot become audible.

The exact external trigger is not claimed as proven yet.

## Planned 0.0.35 containment

Preserve the fast previous-track cache, but enforce an inactive-media invariant:

- every non-current cached/preloaded media element is paused and muted;
- promotion to current explicitly unmutes the selected element;
- if an inactive slot fires a `playing` event anyway, immediately mute and pause it;
- log that unexpected inactive playback was blocked.

Expected diagnostic if Safari tries to revive an inactive slot:

`Blocked unexpected playback from inactive ... slot`

This provides both containment and evidence without discarding the previous-cache optimization.
