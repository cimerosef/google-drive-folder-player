# Edge + Violentmonkey — 0.0.24 full-folder player integration test plan

Date: 2026-09-16

## Goal

Validate only the integration boundary between the already-validated full-folder discovery mechanism and the already-validated direct MP3/WebM playback core.

This is intentionally one conservative step before modifying the complete 0.0.23 main player.

## Setup

1. Disable the 0.0.23 main player and all previous discovery/direct-media probes.
2. Enable only `probes/full-folder-player-integration-probe.user.js` from `dev/0.0.24-full-folder-discovery`.
3. Refresh the Drive Music folder.
4. Confirm the panel title is `Full Folder Player Integration Probe 0.0.1`.

## Test A — discovery feeds the player cache

Click `Discover full folder` and do not manually scroll while it runs.

Expected for the current validated Music folder:

- final cache: **160** items
- **144 MP3**
- **16 WebM**
- Drive list returns near the original scroll position
- the queue area reports that the full-folder cache is ready

The 160 total has already been independently verified by three directional DOM traversals and by the user's manual Ctrl+A count.

## Test B — ordered full queue

Click `Start full queue` with Shuffle OFF.

Expected:

- queue size is **160**
- track 1 starts through direct media
- the next track preloads
- `Next now` works normally
- `Seek last 5s` produces a smooth natural handoff
- no Drive Preview opens for MP3/WebM

## Test C — prove an item beyond the old visible ~50 can play

Click `Play last test`.

Expected:

- the player builds the ordered 160-track cache
- track **160/160** starts directly even though that row is not currently rendered in the Drive DOM
- for the current folder baseline, the tail item is `黑龍 - 盜心賊我的心被你掏了無怨無悔動態歌詞Lyrics.mp3`

This is the key integration proof: playback is driven by the full discovered `{name, Drive ID}` cache rather than by currently visible Drive rows.

## Test D — Shuffle on the full set

Stop playback, turn Shuffle ON, then click `Start full queue`.

Expected:

- queue size remains 160
- order is randomized once when the queue is built
- direct preload follows that shuffled order
- several `Next now` / natural transitions remain smooth

## Test E — Repeat smoke test

Cycle Repeat through ONE and ALL.

Expected:

- Repeat ONE: natural end restarts the current direct track; `Next now` still advances
- Repeat ALL: queue-end behavior remains defined to wrap to item 1

A full 160-track wait is not required in this integration probe; this is only a regression smoke test of the already-validated repeat logic.

## Test F — background handoff

While the panel reports a preloaded next track:

1. click `Seek last 5s`
2. switch to another browser tab immediately
3. wait for the next track to begin

Expected:

- background handoff still succeeds
- no Drive Preview appears
- no multi-second Preview transition delay returns

## Pass criterion

PASS if discovery returns the validated 160-item cache, the queue is 160 tracks, track 160 can be played directly from the discovered Drive ID without requiring its Drive row to be rendered, and normal foreground/background direct-media transitions remain stable.

If this passes, the same full-folder discovery code can be integrated into the complete 0.0.23 main player to produce the actual 0.0.24 development build.
