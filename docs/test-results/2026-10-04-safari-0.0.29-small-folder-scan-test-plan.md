# Safari + Userscripts — 0.0.29 small non-scrollable folder scan

Date: 2026-10-04

## Finding

During Safari SPA-navigation validation, the owner navigated from the 169-track Music folder to a parent Drive location containing only a few visible items.

With two MP3 files directly visible in that location, 0.0.28 still reported:

`Could not identify the Drive folder list.`

The two files themselves were visible and filename-compatible. The failure occurs before collection because `discoverFullFolder()` requires `findScrollContainer()` to return a scrollable container.

For a short Drive list that does not overflow, there may be no scrollable container to identify.

## Classification

General discovery edge case exposed during Safari validation; not currently considered Safari-specific.

Refreshing the page is not expected to fix the behavior because the same 0.0.28 discovery logic would run again.

## Minimal fix

0.0.29 changes only the no-scroller branch of `discoverFullFolder()`:

- if no scroll container is found, perform one ordinary `addRowsToMap()` pass;
- if supported media rows are already rendered, accept those rows as the complete result;
- retain the existing failure behavior when neither a scroll container nor rendered media rows can be found;
- leave the existing scroll-based full-folder discovery path unchanged.

The mature Edge 0.0.28 frozen branch is untouched.

## Safari acceptance test

1. Install/update to 0.0.29 from `dev/safari-compat`.
2. Refresh Google Drive once so the new script instance is loaded.
3. Stay in the parent location containing exactly two directly visible MP3 files.
4. Click `Scan folder`.
5. Expected: `2 tracks · 2 MP3 · 0 WebM`.

After this passes, re-enter the large Music folder and confirm the existing scroll-based path still returns the current complete count (169) before considering the discovery change regression-safe.
