# Edge validation — 0.0.17 direct MP3 two-track preload

Platform: Microsoft Edge + Violentmonkey

Date: 2026-09-16

Branch: `dev/0.0.17-direct-mp3-preload`

Probe: `probes/mp3-two-track-preload-probe.user.js` 0.0.1

## Result

PASS for foreground two-track direct-Audio preload and automatic handoff.

Observed test flow:

- Track A captured from a normal Google Drive file-list row using its stable Drive ID.
- Track B captured from a second MP3 row using its stable Drive ID.
- Both tracks loaded through the direct `drive.usercontent.google.com/download` route with `confirm=t` and the active `authuser` index.
- Both A and B reached `canplay` before A was advanced to its final seconds.
- A played through the script-owned HTMLAudioElement with no Drive Preview UI.
- A was moved to about five seconds before its natural end.
- When A emitted `ended`, the probe immediately called `B.play()`.
- B began playing successfully.
- Reported `A→B audible-start latency: 15 ms`.
- The user reported that the A→B transition sounded smooth and matched expectations.

## Significance

This validates the direct-Audio architecture for MP3 playback in the foreground:

1. Google Drive Preview is not required for playback once the file ID and active account index are known.
2. A following MP3 can be preloaded while the current MP3 is playing.
3. Automatic handoff from an ending track to a preloaded next track can be effectively immediate (15 ms in this run), removing the multi-second Preview-close / Preview-open bottleneck seen in the legacy architecture.

## Remaining gate before main-player integration

The same probe should be tested with the Drive tab hidden before A ends. The key remaining question is whether the browser allows the already-authorized/preloaded B Audio element to start automatically in the background when A reaches `ended`.

Do not replace the stable main player yet. Preserve `stable/0.0.14` until background direct-Audio handoff is validated.
