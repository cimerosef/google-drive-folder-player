# Edge test plan — 0.0.16 media-source architecture probe

Target: Microsoft Edge + Violentmonkey

## Purpose

Determine what Google Drive's native preview actually uses to play MP3/WebM media so we can judge whether a future player can avoid the slow close-preview/open-next-preview transition path.

This is an architecture probe only. It does not replace the validated 0.0.14 player and does not attempt direct playback yet.

The probe observes:

- `audio` / `video` elements, including elements created inside shadow roots that attach after page load;
- calls to `HTMLMediaElement.play()`;
- `MediaSource` object URLs, `addSourceBuffer()` MIME types, and occasional `appendBuffer()` byte counts;
- iframes and whether they are readable from the Drive page;
- Performance Resource Timing entries that look like media delivery endpoints;
- media events such as `playing`, `waiting`, `ended`, `error`, and `encrypted`.

URL query **values are deliberately redacted** in the panel/report. The probe shows only origin/path plus query-key names.

## Setup

1. Disable the main 0.0.15 player for this probe test.
2. Disable the Background Playback Probe and Full-folder Discovery Probe.
3. Enable only `probes/media-source-probe.user.js` version 0.0.1 from `dev/0.0.16-media-source-probe`.
4. Refresh Google Drive so the `document-start` hooks are installed before Drive creates its preview player.
5. Open the normal music folder.

## MP3 test

1. Double-click one MP3 manually so Drive opens its native preview.
2. Let it play for about 10–15 seconds.
3. Click `Snapshot now` in the Media Source Probe panel.
4. Capture a screenshot of the panel. If useful, use `Copy report` and provide the relevant lines.
5. Close the MP3 preview manually.

## WebM test

1. Double-click one WebM file manually.
2. Let it play for about 10–15 seconds.
3. Click `Snapshot now`.
4. Capture the panel again.

## Key evidence to look for

### Case A — direct media URL

Promising evidence would look like:

- `MEDIA discovered ... src=https://...`
- `MEDIA play() called ... src=https://...`

If Drive exposes a directly reusable HTTP(S) `currentSrc`, the next experiment can test whether a separate hidden/audio element can preload and play it without reopening Drive Preview.

### Case B — blob URL + MediaSource

Evidence may look like:

- `createObjectURL(MediaSource) -> blob:<redacted>`
- `MSE addSourceBuffer: audio/...`
- `MSE appendBuffer ...`
- `MEDIA ... src=blob:<redacted>`

That means Drive is assembling the stream with Media Source Extensions. It may still be technically possible to build our own playback path, but the next probe would need to understand the media request/chunk mechanism rather than simply reusing one URL.

### Case C — inaccessible iframe

If the actual player lives in a cross-origin iframe, expect lines such as:

- `IFRAME cross-origin/inaccessible: ...`

In that case the next experiment may need an additional userscript `@match` for the iframe's host rather than trying to inspect it from the top Drive document.

### Case D — encrypted media

An `encrypted` media event would materially change the feasibility assessment. Do not attempt to bypass DRM; record the finding only.

## Safety / scope

- No Google API or OAuth.
- No download action.
- No media bytes are copied or exposed.
- No query-string token values are logged.
- The probe wraps a few native browser methods only to observe arguments/results and immediately delegates to the original implementation.
- The stable 0.0.14 playback branch remains untouched.

## Expected next decision

After one MP3 and one WebM result, choose the smallest next experiment based on the observed playback architecture. Do not modify the main player until this media-source path is proven viable.
